# External supervisor runtime — planned D07c

This refines [the guarded package protocol](guarded-package-v1.md). It defines
the separately installed tool, not an application execution feature or a claim
of qualification. Ordinary invocation remains unavailable until its exact native
client/runtime, TLS, transcript and transaction matrix passes.
The candidate's exact frames, command sequence and outcome codes are in
[ordered protocol v1](guarded-supervisor-protocol-v1.md).

## Distribution and dependency boundary

Implement a plain Java 21 entry point in `backend/tools/guarded-supervisor`.
The server never depends on this module. Process creation, native-client input,
credential prompting and transaction execution exist only in the tools module;
the web application has no execution route, startup switch or client launcher.

Attach an explicit `classes` classifier containing the server's ordinary classes
and contract resources before Spring Boot repackaging. The supervisor may depend
on that classifier to reuse strict package admission and trusted templates. Do
not depend on the incidental `.original` file or execute a Boot archive as a
dependency. Exclude all server transitive dependencies and explicitly enumerate
the core/parser/schema dependencies actually needed by these mechanisms. Do not
ship Spring, servlet/security, JDBC drivers or SQLite in the supervisor runtime.
The classifier is a packaging bridge, not proof that every server class is used
or a new permission boundary.

Produce a separate versioned directory/archive with its CLI JAR, fixed dependency
JARs, launcher, license notices and SHA-256 inventory. The launcher uses an
explicit installation-relative classpath, never the package directory, current
directory, CLASSPATH, downloaded helpers or a wildcard supplied by the operator.
Build/test this distribution separately from web-image publication. Verify launch
from an unrelated directory and inspect the web image for absence of the tool and
native clients. Runtime qualification records pin Linux amd64, the exact Java 21
build and the native installation identity; Java language compatibility alone
does not qualify a runtime.

## Invocation and package admission

The only ordinary operation is:

```text
environment-studio-guarded apply --package ABSOLUTE_PATH --sha256 LOWERCASE_SHA256 --configuration ABSOLUTE_PATH --destination ID
```

Reject unknown, duplicate or missing arguments before prompting or launching a
process. There is no credential argument, environment credential, stdin password
automation flag, shell command, SQL override, client override or ordinary test
mode. Package/configuration paths are normalized absolute paths to readable
regular files with no symlink components. Reject malformed Unicode, NUL and line
breaks in paths; retain paths only as necessary for the operation. Configuration
and packages stay external to the checkout, image and metadata workspace.

Open each admitted file once without following links. Hash/read the same bounded
package bytes that are inspected and exactly regenerated; never check one path
then reopen different bytes for execution. Admission must independently match the
operator-supplied whole-archive digest, all four strict members, their closed
schema/semantic constraints and the trusted template's complete generated bytes.
Oracle block boundaries come only from that same generator. No client or password
reader starts until package, destination, runtime and trust admission all pass.

External file paths require directories and files controlled only by root or the
invoking operator, with no untrusted write authority. Reject group/other write
access and unsupported ownership/ACL evidence. A world-writable ancestor is
eligible only when qualified sticky-directory protection prevents replacement of
the next owned component; otherwise refuse it. Traverse with no-follow directory
handles and check the final regular-file type before the single bounded read.
This prerequisite does not claim resistance to concurrent changes by root or the
same operator UID. Java pathname checks alone do not prove an atomic regular-file
open against a privileged actor swapping in a FIFO; no such guarantee is made.

## Closed external configuration

The UTF-8 JSON root contains exactly `formatVersion`, `sessionLauncher`,
`terminalControl`, `clients` and `destinations`. `formatVersion` is
`es-guarded-supervisor-config-v1`.
Bound the file to 1 MiB, depth 8 and 10,000 tokens. Reject duplicate/unknown fields,
trailing input, malformed scalars and noncanonical integer tokens. No YAML,
environment interpolation, includes or connection-property maps are accepted.

`sessionLauncher` contains exactly `path` and `sha256`. It identifies the trusted
Linux session-launch utility used with a fixed argument list; a shell is never
involved. Its effective behavior/version/hash must be independently qualified,
including a new session without a controlling terminal and exact child ownership.
`terminalControl` has the same path/hash shape and pins the qualified terminal
utility used only with fixed operations to capture state, disable echo and restore
the exact state. Neither helper accepts an operator-supplied command or arguments.

`clients` has one or two entries, with no duplicate family. Each entry contains
exactly `family`, `version`, `runtimeRoot`, `runtimeIdentity`, `executableSha256`
and, for SQL*Plus only, `orapkiSha256`. Family/version is `psql`/`18.6` or
`sqlplus`/`23.26.3.0.0`. Executables resolve to `runtimeRoot/bin/psql`,
`runtimeRoot/bin/sqlplus` and `runtimeRoot/bin/orapki`; there are no caller-supplied
argument lists. All hashes/identities are 64 lowercase hex characters. The
read-only trusted installation and its libraries/scripts must match an installed
qualification record for `runtimeIdentity`; hashing an entry executable alone
does not establish the identity of its libraries or script interpreter. Unknown
runtime identities refuse. Native clients are separately installed through the
operator's existing distribution process, not extracted from an export.

`destinations` has 1–32 entries with unique lowercase IDs. Each entry contains
exactly `id`, `engine`, `host`, `port`, `database`, `transportIdentity`,
`provisioningPolicyVersion`, `expectedPhysicalIdentity` and `trustMaterial`.
Use the scalar bounds and physical-identity shapes of
[hosted destinations](hosted-destinations-v1.md), without its owners or observation
account policy. Engine is `postgresql` or `oracle` and requires its matching client.
The selected entry must exactly equal the manifest's destination/engine fields;
the manifest cannot add or override an endpoint. `trustMaterial` contains exactly
`path` and `sha256`, naming an externally approved certificate-only PEM bundle.
Trust input is at most 1 MiB/128 certificates, with at least one valid X.509
certificate and no private key, other PEM block or non-whitespace trailing data.
It is hashed and parsed from one bounded read before any secret is requested.

Configuration labels and digests do not self-approve a runtime or transport
policy. Match them against the installed qualified combination and independently
provisioned external configuration. The initial compiled qualification registry
is empty. Only exact-client evidence permits a later entry; there is no wildcard,
caller-supplied PASS, fallback or configuration flag that enables a missing entry.

## Native trust and process isolation

Ordinary execution requires verified TLS. PostgreSQL uses fixed `sslmode=verify-full`
and a private temporary certificate file written from the already admitted root
certificate bytes. Never reopen the original trust path for client use. Disable inherited libpq service,
password, SSL client-key, startup/history/pager and connection options. Do not
rely on default certificate paths, `prefer` or `require`.

For Oracle, build a new certificate-only auto-login wallet from the validated
PEM certificates using the pinned `orapki` and its fixed commands. Create it in
an exclusively owned private temporary directory; never import an existing wallet,
credential store, user certificate or key. Verify the resulting trust set exactly
and qualify the passwordless create/add sequence. Use a generated closed TCPS
descriptor with the explicit wallet location and hostname matching enabled.
Missing/corrupt trust or a mismatch must refuse without consulting system trust.
No direct native SQL*Plus PEM support is assumed. Temporary files contain only
public certificates and tool-owned non-secret settings, and receive bounded
owned-path cleanup. Never write credentials, package payloads or client output.

Clear inherited environment and supply only the qualified fixed locale/encoding,
installation paths and tool-owned Oracle configuration needed by that client.
No inherited `JAVA_TOOL_OPTIONS`, `JDK_JAVA_OPTIONS`, startup paths, tracing,
service files, passwords or arbitrary library paths enter the child. Qualify the
complete effective environment, startup suppression, empty owned working
directory and closed descriptors; executable hashing alone is insufficient.

The parent requires a controlling console for ordinary credential entry, disables
echo and owns mutable bounded buffers. Bound allocation while reading, not only
after an unbounded `Console.readPassword()` call. Restore the captured terminal
state on success, refusal, interruption and shutdown; a missing console or failed
terminal setup refuses. Tests inject a reader through code rather than a public
flag. Passwords/tokens never enter argv or environment. Stock psql receives the
interactively supplied account name through the fixed `-U` argument, making that
identifier visible to local process inspection; SQL*Plus receives it only through
owned CONNECT input. This native-client property must be disclosed before entry
and explicitly accepted in the external account/privacy qualification. It cannot
qualify a confidential username by silently calling it non-secret. Account names
remain absent from supervisor output, stored configuration and packages. The
supervisor's public invocation still accepts no username argument.
The child has no controlling terminal, one owned stdin and one merged output pipe.
All prompt, encoding, time/frame limits and one-commit rules remain those of the
parent protocol. No asynchronous credential or request queue is introduced.

## Outcome and qualification

Emit only tool-owned status codes, never native output, SQL, XML, identifiers,
credential values or exception text. Before commit, refusal/error cannot send
COMMIT. Report cleanup Complete only from the protocol's actual acknowledged
cleanup; process disappearance alone is insufficient. After any commit byte may
have been sent, missing or ambiguous acknowledgement is UNKNOWN and is never
automatically retried. APPLIED requires the qualified ordered acknowledgement and
clean native exit. Fresh readback remains a separate state comparison.

Tests must include altered members and regenerated SQL, argument/configuration
closure, file replacement, unqualified runtime, hostile environment/startup files,
one prompt and credential canaries, merged-output errors before readiness,
quiet/trickling/oversized output, EOF/death, cleanup uncertainty, wrong/untrusted
TLS endpoints, no fallback, lost commit acknowledgement and complete both-engine
target/rollback witnesses. Existing template rollback probes do not satisfy the
supervisor's commit or TLS gates.
